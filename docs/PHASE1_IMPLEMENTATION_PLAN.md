# Phase 1 前后端协作顺序
当前成果是契约评审基线。后端用现有 audit/v2-phase-0，前端为 frontend/v2-design；由前端负责人在自己的 worktree cherry-pick 本次仅 docs 的提交，或在其功能分支合并。接口变化先更新映射和样例，再评审后落代码。项目基址仅在 services 客户端配置；本地实际前端 origin 须与 FastAPI CORS 一致。

|次序|后端任务与依赖|前端并行任务|交付门槛|
|---|---|---|---|
|1 当前交接|以 PHASE1_API_MAPPING 为清单，按 operation + 成功状态核对；后续补 response_model、PDF 媒体类型和实际错误格式的 OpenAPI 描述。保留 v1 路径与 wire 字段。|建 types/contracts.ts 和统一 fetch 适配层。金额保持字符串，处理 204、PDF、422 字符串和可空推荐。|用只读接口接入 Overview、订单列表/详情、运行历史、对比、报告；无需迁移。|
|2 UI 原型|评审 NEW 契约、来源分类、角色与双审批状态机；提供脱敏固定 JSON fixture。|中文默认，建立 Inbox 双入口、证据侧栏、回复编辑与审批界面；模拟数据明确标注。|前端用同一例子演示缺字段、证据过期、拒绝和重新提交。NEW 不调用生产路径。|
|3 Inbox 与建单|先建身份与租户、受控文件区、队列，再接 Gmail/Graph 或独立上传，落原件、抽取版本及带证据提案。批准当前 revision 与创建 Deal 同事务，唯一键防重复建单。|接任务状态/字段证据及审批回执。|单独测试邮箱与文件入口，附件重放、解析失败、无权限、修改后旧批准无效、审批并发只产生一单。|
|4 Intelligence|接入有授权的企业背景、国家政策、产品监管来源；记录来源 URL、采集/生效/过期时间、可信度依据与冲突；匹配产品 SKU/单位需确认。|展示事实、推测、缺失、引用与更新时间。|没有证据不得转为事实或自动写入成本；CN→US 首演，另测其他目的地不误用美国规则。|
|5 Reply Studio|从已选方案生成双语草稿，版本化收件人/正文/附件，批准后写事务 outbox，投递回执与超时对账。|可预览更正和重新审批；调用发送前展示完整收件人。|改动报价/地址后原授权失效；无审批不能发送；测试收件箱验证，不将模拟送达计入真实验收。|
|6 集成与回归|隔离数据库演练增量迁移、V1 归属回填与恢复工具升级；补 DTO 契约快照、404/409/422/500、Decimal 字符串、超时和跨租户测试。|Edge 测双入口、三态优化、审批与报告下载；新旧前端分别走 V1 订单闭环。|运行原 14 项全套，重放旧优化、比较原 PDF 字节；失败可关闭 V2 入口并保留历史记录。|

首个前端工单：在独立分支先完成真实看板→订单→运行→对比的只读路径，以及两种询盘来源汇入同一审核页的 fixture 原型。将 API 状态标记与 fixture 分目录；明示旧 selected_by 只是署名，建单审批与发件审批各自绑定版本。后端在下一轮评审通过后才实施以上扩展。
