# V2 架构建议（待批准）
保留 Next.js → FastAPI → SQLAlchemy/PostgreSQL 的模块化单体。另启一个同仓 Python worker 进程处理耗时或可重试任务；API、worker 使用同一套领域校验。第一版优先以 PostgreSQL 作持久任务队列，Windows 用独立前台进程或服务启动。外部接入先限制在沙盒账户；尚无已验证的提供商连接。

## 从输入到回复的状态与责任
邮件同步、文件上传是同级入口，均产出 inquiry 和不可变来源标识。原件进入受控文件区，数据库保存所有者、摘要、大小和定位键。接收事务同时创建解析任务。worker 解析、抽取并并行准备公司、商品、政策证据。缺失和冲突保留为待核实；分析结果形成有版本的建单提案。分析草稿可以试算；正式订单只能由已获授权的建单审批事务创建。随后复用冻结的财务、优化、决策与报告逻辑。报价草稿绑定已选方案，校对收件人、币种、语言、附件、正文和报价有效期后，需要第二次审批才进入发送队列。

## 安全和可运维性
租户隔离应覆盖搜索、后台任务、报告/PDF 和附件下载。凭据用 Windows 安全存储或部署方密钥服务，DB 存引用；密钥轮换、撤销与审计需可演练。研究抓取限制协议及目标域、屏蔽内网和重定向绕行；展示提取文本时转义。日志仅保留关联 ID、错误类型、延迟、重试与配额，不记录信件、令牌、附件原文。跨系统使用关联 ID 跟踪询盘→订单→报价。监测队列年龄、解析失败率、审批积压和待对账的发送。V1 本机进程和旧只读报告继续可用；新集成通过开关逐租户启用。
